Okay, you  can see here the host name has changed. Next let’s set an enable secret. If no enable  secret is set, when you connect via Telnet or SSH it won’t let you access privileged exec mode. Now,  there is a way to change that, you can manually set a high privilege level on the user you create,  but I’ll cover that in a later video on security. For now just make sure you have an enable secret  configured, so you can access privileged exec mode when connecting remotely. So, ENABLE SECRET ccna.  These passwords are case-sensitive, by the way. Next, let’s create a login account. I’ll  cover more details about user accounts in the security section, but the basic command is  USERNAME, then the username, jeremy in this case, then either PASSWORD or SECRET, I’ll use  SECRET, and finally the password itself, ccna. As I mentioned earlier in the course, if you  use PASSWORD the password is stored in plain text, not encrypted. Even if you use the  SERVICE PASSWORD-ENCRYPTION command, the encryption isn’t as strong  as if you use SECRET instead. Next let’s configure SW2 for remote management  by configuring an IP address on its VLAN1 SVI. INTERFACE VLAN1. IP ADDRESS 192.168.2.253  255.255.255.0. In packet tracer, at least this model of switch, the SVI is shutdown by  default, so let’s enable it with NO SHUTDOWN. Then we get two Syslog messages saying the  interface came up. Okay, finally I’ll configure SW2’s default gateway. EXIT. IP DEFAULT-GATEWAY  192.168.2.254. If a host is in SW2’s local subnet, SW2 can communicate directly with it. However  to communicate with hosts outside of the local subnet, SW2 needs to know its default gateway,  so that’s why we have to use that command. Next, in step 2 we’ll configure a few  security settings on the console line. LINE CONSOLE 0. There is only one  console line, so the number is always 0. Now let’s configure local authentication. LOGIN LOCAL. So, to connect to the console line a user  will have to use the account we configured before. Then, I’ll set the exec timeout. EXEC-TIMEOUT 5.  Note that you don’t have to specify 0 seconds, you can just specify 5 minutes and then hit enter.  Now to test the local authentication I’ll use END to return to privileged exec mode, and then  EXIT to log out. Hit enter, and now I’m asked for a username, jeremy, and a password,  ccna. ENABLE. And again, password of ccna. Okay, now step 3 is to configure  SW2 for remote access via SSH. First, let me try to generate  RSA keys. CONF T. CRYPTO KEY GENERATE RSA. Since SW2 doesn’t have a domain  name yet, it can’t generate the keys. So, let’s specify the domain name.  IP DOMAIN NAME jeremysitlab.com. And now I’ll try to generate the keys again.  CRYPTO KEY GENERATE RSA. And I’ll specify the key modulus size of 2048 bits, and it works.  RSA keys are used for encryption and decryption, by the way. I’ll give some more detail in  the security section of the course. Okay, now before configuring the VTY lines I’m going  to configure an ACL to limit access to PC1 only. I’ll just use a simple standard ACL. ACCESS-LIST  1 PERMIT HOST 192.168.1.1. I want to limit access to SSH only, no Telnet, but we can do that with  the TRANSPORT INPUT SSH command so there isn’t actually any need to specify the port in the ACL.  Now I’ll configure the VTY lines. LINE VTY 0 15. First I’ll configure local authentication. LOGIN  LOCAL. And the same 5 minute exec timeout as on the console lines. EXEC-TIMEOUT 5. Then I’ll  restrict access to SSH only, TRANSPORT INPUT SSH. And finally, apply the ACL I configured  before. ACCESS-CLASS 1 IN. That’s it. So, let’s test it out. First, I’ll try from R2,  which shouldn’t be able to connect because of the ACL. First, I’ll try a ping. ENABLE. PING  192.168.2.253. Okay, so R2 is able to ping SW2. How about SSH? SSH -L jeremy 192.168.2.253.  And the connection is refused by SW2. Perfect. Next I’ll try from PC1, which should be able  to SSH because the ACL permits PC1 only. First I’ll try to ping SW2  from PC1. PING 192.168.2.253. The ARP process can be slow in packet tracer, so  a few pings might fail, but after that the pings will succeed. So, PC1 can reach SW2 with ping,  how about SSH? SSH -L jeremy 192.168.2.253. Okay, enter the password of ccna and we’re in. So, PC1  was able to connect to the CLI of SW2 using SSH.
